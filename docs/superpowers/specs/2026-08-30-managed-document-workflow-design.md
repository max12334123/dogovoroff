# Управляемый документооборот по делу

Статус: дизайн утверждён пользователем 30.08.2026; реализация не начата.

## Контекст

Личный кабинет уже позволяет участнику дела загружать документы в приватный Supabase
Storage, регистрировать метаданные в PostgreSQL и скачивать доступные файлы. Сотрудник
видит документы в карточке дела. Однако файл не связан с конкретным запросом юриста,
а клиент ориентируется только по одному общему полю «Следующий шаг».

Новый модуль должен превратить пассивный реестр файлов в понятный процесс: сотрудник
запрашивает комплект, клиент прикладывает несколько файлов и явно отправляет их на
проверку, после чего сотрудник принимает комплект либо возвращает его с пояснением.

## Цели

- Показать клиенту точный список требуемых комплектов и их состояние.
- Разрешить прикреплять к одному запросу несколько файлов.
- Отделить документные запросы от общего поля «Следующий шаг».
- Сохранить совместимость с уже загруженными документами.
- Защитить все операции на уровне PostgreSQL и RLS, а не только интерфейса.
- Сохранить безопасные уведомления и технический аудит без чувствительного содержимого.
- Подготовить структурированную основу для будущего, отдельно согласуемого AI-анализа.

## Не входит в первый релиз

- AI-чтение, распознавание, классификация или преобразование документов.
- Антивирусная проверка содержимого.
- Физическое удаление объектов Storage.
- Полная история текстов замечаний по каждой итерации; хранится последнее замечание.
- Email-, Telegram- и push-уведомления.
- Универсальная система задач, встречи, платежи и клиентские дедлайны вне документов.
- Изменение юридических документов сайта и политики сроков хранения.

## Рассмотренные подходы

### Выбранный: отдельные запросы документов

Создаётся отдельная таблица запросов, а существующий документ получает необязательную
ссылку на запрос. Модель поддерживает несколько запросов и файлов, сохраняет историю
состояний через события и не ломает прежние документы.

### Отклонённый: расширение поля «Следующий шаг»

Подход потребовал бы хранить скрытую структуру внутри одного поля, позволял бы вести
только один комплект и смешивал бы документную работу с встречами и ответами клиента.

### Отклонённый: универсальная система задач

Она дала бы больше гибкости, но потребовала бы отдельной модели типов задач, исполнителей,
зависимостей и уведомлений. Для текущей потребности это преждевременное усложнение.

## Пользовательский сценарий

### Сотрудник

1. Открывает карточку доступного дела.
2. Нажимает «Запросить документы».
3. Указывает обязательное название, необязательную инструкцию и необязательную дату.
4. До первой загрузки клиента может исправить реквизиты запроса.
5. Видит запрос со статусом «Ожидаем документы».
6. После отправки клиентом скачивает активные файлы.
7. Выбирает «Принять комплект» либо «Вернуть на исправление».
8. При возврате обязательно вводит понятное пояснение.
9. При необходимости отменяет ещё не принятый запрос. Принятый запрос не переоткрывается;
   для новых материалов создаётся новый запрос.

### Клиент

1. На главной кабинета видит ближайший незавершённый запрос в блоке «Требуется от вас».
2. Открывает карточку запроса в разделе «Документы».
3. По одному прикрепляет до 20 активных файлов.
4. Может отозвать ошибочный файл до отправки; метаданные получают статус «В архиве»,
   физический объект остаётся приватным до появления общей политики удаления.
5. Явно нажимает «Отправить комплект на проверку».
6. При возврате видит последнее пояснение, добавляет или архивирует файлы и отправляет
   комплект повторно.
7. После принятия видит финальный статус без возможности изменить комплект.

Существующие документы без запроса отображаются в блоке «Другие документы» и продолжают
работать по прежним правилам.

## Состояния и переходы

В PostgreSQL добавляется enum `document_request_status`:

| Значение | Интерфейс | Кто устанавливает |
| --- | --- | --- |
| `requested` | Ожидаем документы | сотрудник при создании |
| `submitted` | Получено, на проверке | клиент |
| `changes_requested` | Нужно исправить | сотрудник |
| `accepted` | Принято | сотрудник |
| `cancelled` | Отменено | сотрудник |

Разрешённые переходы:

- создание сотрудником → `requested`;
- `requested` или `changes_requested` → `submitted`, если есть хотя бы один активный файл;
- `submitted` → `accepted`;
- `submitted` → `changes_requested` только с непустым пояснением;
- `requested`, `submitted` или `changes_requested` → `cancelled`;
- `accepted` и `cancelled` являются конечными состояниями.

Проверка текущего состояния и запись каждой команды выполняются внутри одной
транзакционной RPC-функции.
Повтор идентичной уже завершённой команды возвращает безопасный успешный результат. Команда,
противоречащая текущему состоянию, не перезаписывает данные и просит интерфейс обновиться.

## Модель данных

### `public.document_requests`

- `id uuid primary key default gen_random_uuid()`;
- `matter_id uuid not null references public.matters(id) on delete cascade`;
- `title text not null`, после `btrim` от 1 до 240 символов;
- `instructions text`, после `btrim` не более 2000 символов;
- `due_on date` — календарная дата без времени и часового пояса;
- `status document_request_status not null default 'requested'`;
- `last_review_note text`, после `btrim` не более 2000 символов;
- `created_by uuid not null references auth.users(id) on delete restrict`;
- `reviewed_by uuid references auth.users(id) on delete set null`;
- `submitted_at timestamptz`;
- `reviewed_at timestamptz`;
- `created_at timestamptz not null default now()`;
- `updated_at timestamptz not null default now()`.

Индексы:

- `(matter_id, status, due_on)` для карточки дела и ближайшего запроса;
- `(created_by)` и частичный `(reviewed_by)` для внешних ключей и проверок.

Последнее замечание сохраняется при повторной отправке, чтобы клиент мог свериться с ним.
После принятия интерфейс его скрывает. Каждое изменение состояния отдельно фиксируется
без содержимого замечания в `matter_events` и техническом аудите.

### Изменение `public.documents`

Добавляется `request_id uuid references public.document_requests(id)`. Поле необязательно:
`null` означает обычный документ из блока «Другие документы». Удаление запроса через API
не разрешается, поэтому каскадное удаление связи не требуется.

Один документ принадлежит не более чем одному запросу. Повторное использование файла в
нескольких запросах не входит в MVP.

Активным считается связанный документ со статусом, отличным от `archived`. Ограничение в
20 активных файлов проверяется внутри операции регистрации и повторно перед отправкой.
После принятия запроса активные связанные документы атомарно получают существующий статус
`ready`. При возврате они остаются доступными; клиент может архивировать ненужные версии и
добавить новые.

Storage-путь не меняется и сохраняет вид `<matter-id>/<document-id>/document.<ext>`.
Название запроса, email и исходное имя файла в путь не добавляются.

## Авторизация и RLS

### Чтение

`document_requests` доступны только пользователю, для которого
`private.can_access_matter(matter_id)` возвращает `true`. Это сохраняет существующую
изоляцию клиента A, клиента B и сотрудников разных организаций.

### Запись

Прямые `insert`, `update` и `delete` для `anon` и `authenticated` на новой таблице
отзываются. Записи выполняются узкими `security definer` RPC-функциями с пустым
`search_path`, полными именами объектов и повторной проверкой `auth.uid()`:

- `create_document_request` — только пользователь, который может управлять делом;
- `update_document_request` — тот же сотрудник, только пока запрос имеет статус `requested`
  и к нему ещё не прикреплён активный файл;
- `register_document_request_file` — только клиентский участник, для существующего объекта
  текущего пользователя в Storage и изменяемого запроса того же дела;
- `submit_document_request` — только клиентский участник этого дела;
- `review_document_request` — только пользователь, который может управлять делом;
- `cancel_document_request` — только пользователь, который может управлять делом;
- `withdraw_document_request_file` — только загрузивший файл клиент, пока запрос допускает
  клиентские изменения.

`execute` явно отзывается у `public` и `anon`; роли `authenticated` выдаются только нужные
функции. Ни одна RPC не принимает organization ID от браузера как источник полномочий.

Действующая прямая вставка `documents` сохраняется только для обычного документа с
`request_id is null`. Связанный с запросом файл регистрируется через отдельную RPC: она
проверяет тот же `matter_id`, статус `requested` или `changes_requested`, клиентское участие,
канонический путь и существование объекта текущего пользователя в приватном bucket.
Регистрация сериализуется для одного запроса и атомарно не допускает более 20 активных
файлов даже при одновременных командах. Прямые обновление и удаление документа не выдаются.

## Серверные контракты

Предусматриваются отдельные server actions с одинаковой схемой ответа
`{ ok: boolean, message: string, data?: object }`:

- `createDocumentRequest`;
- `updateDocumentRequest`;
- `submitDocumentRequest`;
- `reviewDocumentRequest`;
- `cancelDocumentRequest`;
- `withdrawDocumentRequestFile`.

Каждое действие:

1. нормализует и ограничивает входные данные;
2. получает пользователя через `auth.getClaims()`;
3. вызывает одну узкую RPC-функцию;
4. не раскрывает клиенту коды и тексты ошибок PostgreSQL;
5. обновляет только `/cabinet` и `/staff` после успеха.

Текущий `registerMatterDocument` получает необязательный `requestId`. UUID документа
создаётся до загрузки и остаётся стабильным при повторе. Для связанного файла server action
после проверки Storage вызывает `register_document_request_file`, а не прямой `insert`.
Если объект Storage и полностью совпадающая строка документа уже существуют, повтор
регистрации считается успешным.

## Компоненты интерфейса

Новый код размещается в `features/document-requests`, а не добавляется целиком в уже крупные
клиентский и служебный компоненты:

- чистый доменный модуль: статусы, подписи, сортировка, переходы и валидация;
- server actions для команд;
- клиентский список и карточка запроса;
- панель загрузки и отправки комплекта;
- форма создания запроса для сотрудника;
- панель проверки, возврата и принятия.

`loadCabinetData` получает запросы доступных дел и поле `documents.request_id`, группирует
их по делу и передаёт компонентам только нормализованную модель.

### Кабинет клиента

- На обзоре показывается запрос, который требует действия клиента: сначала
  `changes_requested`, затем `requested`; внутри группы — ближайший `due_on`, даты `null`
  идут последними, после чего используется `created_at`.
- Если все комплекты уже отправлены, обзор показывает спокойный статус «На проверке», а не
  призыв загрузить файл.
- Запрос, требующий действия клиента, имеет приоритет над общим `nextAction`, но не изменяет
  его в базе.
- Раздел «Документы» содержит «Запрошено» и «Другие документы».
- У карточки один контекстный главный вызов: загрузить, отправить повторно или посмотреть
  результат.

### Панель сотрудника

- Блок запросов находится внутри карточки дела рядом со следующим шагом и документами.
- В MVP отдельный глобальный раздел навигации не создаётся.
- Сотрудник видит число файлов, сроки и состояние, но скачивает файлы по одному через
  действующий приватный механизм.

### Мобильность и доступность

- На узком экране используются карточки без горизонтальной таблицы.
- Минимальный размер интерактивной области сохраняется не менее 44 CSS-пикселей.
- Статус всегда написан текстом и не передаётся только цветом.
- Ошибки и успехи используют `aria-live`; формы имеют явные подписи.
- После мутации фокус переводится на обновлённую карточку, а при ошибке — на сообщение.
- Длинные названия переносятся и не расширяют страницу.

## Уведомления и аудит

Переходы создают типизированные события с нейтральной копией:

- создан запрос документов;
- комплект отправлен на проверку;
- комплект возвращён на исправление;
- комплект принят;
- запрос отменён.

Центр уведомлений получает только allowlist-тип, UUID доступного дела и время. Название
запроса, имена файлов, инструкция и замечание в уведомление не попадают.

Технический аудит хранит тип команды, организацию, дело и время, но не тексты, имена файлов,
email или содержимое документов. Содержимое последнего замечания доступно только через RLS
самой записи запроса.

## Обработка ошибок и идемпотентность

- Сбой одного файла не меняет состояние запроса и не скрывает успешно зарегистрированные
  файлы.
- Отправка запрещена без хотя бы одного активного связанного документа.
- Повтор регистрации того же стабильного UUID с совпадающими метаданными успешен; конфликт
  с другими данными отклоняется.
- Повтор уже применённой команды перехода возвращает текущее состояние без новой записи.
- Устаревший или недопустимый переход не изменяет данные и предлагает обновить карточку.
- Если объект успешно попал в Storage, а регистрация метаданных завершилась ошибкой,
  повтор использует тот же UUID. Полная автоматическая очистка оставшихся невидимых объектов
  остаётся отдельной задачей после утверждения политики удаления.
- В серверных логах допустимы только технический код и статус ошибки без пользовательского
  содержимого.

## Проверки

### Модульные

- нормализация названия, инструкции, даты и замечания;
- все допустимые и запрещённые переходы;
- сортировка ближайшего запроса;
- лимит активных файлов;
- безопасная модель уведомления;
- идемпотентная регистрация документа.

### Серверные

- отсутствующая и истёкшая сессия;
- корректные RPC-параметры;
- ограниченное редактирование запроса до первой клиентской загрузки;
- безопасное преобразование ошибок;
- повтор команды и повтор регистрации;
- revalidation только после успеха.

### Транзакционные SQL

На бесплатном изолированном `dogovoroff-test` выполняются сценарии гостя, клиента A,
клиента B, юриста и администратора:

- создание доступным сотрудником и отказ клиенту;
- чтение только участниками дела;
- невозможность доступа клиента A к данным клиента B;
- привязка нескольких файлов и запрет чужого либо закрытого запроса;
- отправка, возврат, повторная отправка, принятие и отмена;
- обязательное замечание при возврате;
- запрет прямой записи и недопустимых переходов;
- транзакционный `rollback` и отсутствие синтетических строк после проверки.

### Браузерные

- полный путь на desktop и мобильной ширине;
- отдельные аккаунты клиента A, клиента B, юриста и администратора;
- загрузка нескольких небольших синтетических файлов;
- сетевой повтор без дубликатов;
- клавиатура, видимый фокус, `aria-live` и длинные строки;
- прежние документы без запроса остаются доступными.

Перед завершением выполняются `npm test`, production-сборка, `git diff --check`, проверка
итогового diff и Supabase advisors. Успех не заявляется без фактического запуска команд.

## Порядок выпуска

1. Реализовать аддитивную миграцию и код без изменения Production.
2. Применить миграцию только к `dogovoroff-test`.
3. Выполнить SQL-, серверные и браузерные проверки на синтетических данных.
4. Проверить Preview, связанный с тестовым контуром.
5. Представить результат и отдельно запросить разрешение на Production-миграцию.
6. После разрешения сначала применить аддитивную миграцию, затем опубликовать код.
7. Проверить авторизацию, `/cabinet`, `/staff`, журналы, health endpoint и основной сценарий.

Если интерфейс потребуется откатить, предыдущая версия сайта не использует новую таблицу и
продолжит работать. Таблица, enum и nullable-колонка при откате не удаляются.

## Риски и ограничения

- Без антивируса файлы нельзя автоматически открывать, преобразовывать или передавать AI.
- Storage и PostgreSQL не имеют общей транзакции; идемпотентность уменьшает риск, но не
  заменяет будущую cleanup-задачу.
- Физическое удаление и сроки хранения требуют отдельного решения до массовой работы с
  реальными материалами.
- Уведомления появляются после обновления защищённой страницы; Realtime и внешняя доставка
  не входят в этот релиз.
- Последнее замечание сохраняется, но полноценный журнал текстовых рецензий не создаётся.

## Критерии готовности

- Сотрудник создаёт несколько запросов в доступном деле.
- Клиент прикладывает до 20 активных файлов к одному запросу и явно отправляет комплект.
- Сотрудник принимает комплект или возвращает его с обязательным пояснением.
- Клиент может повторно отправить исправленный комплект.
- Принятые и отменённые запросы неизменяемы.
- Старые документы без запроса продолжают работать.
- Клиент A не может получить запросы или документы клиента B ни через UI, ни прямым API.
- Уведомления и аудит не содержат чувствительных текстов и имён файлов.
