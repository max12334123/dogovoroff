# ADR 0002: изолированный smoke-тест и граница административных RPC

Статус: принято и проверено на изолированном Supabase-проекте 30.08.2026.

## Контекст

Для кабинета нужно подтвердить не только сборку, но и фактическую изоляцию RLS
для клиента A, клиента B, юриста, администратора и гостя. В репозитории есть
четыре транзакционных сценария: `supabase/tests/rls-isolation-smoke.sql`,
`supabase/tests/staff-assignment-smoke.sql`,
`supabase/tests/matter-management-smoke.sql`,
`supabase/tests/intake-inbox-smoke.sql` и отдельная read-only команда
`npm run supabase:smoke` с временными access token.

Проверка должна выполняться только на бесплатном изолированном проекте
`dogovoroff-test`. Production-проект и реальные данные не используются.

## Решение

- До появления временных тестовых токенов и UUID дел команда остаётся в режиме
  безопасного skip: скрипт не создаёт Supabase-клиент и не делает сетевых запросов.
- SQL-сценарии запускаются только в изолированном проекте и завершаются
  `rollback`; после запуска дополнительно проверяется отсутствие синтетических строк.
- Production DDL, миграции и публикация не выполняются в рамках smoke-теста.
- Административные RPC (`list_assignable_staff`,
  `create_matter_for_client_email`, а после применения миграции также
  `update_matter_workflow`) остаются узкими функциями с повторной проверкой роли,
  организационной принадлежности и входных данных.
- Supabase Database Advisor предупреждает о `SECURITY DEFINER` в exposed-схеме.
  Это намеренное ограничение текущего MVP: функции нужны server action для
  точного поиска подтверждённого email и атомарной записи, а внутри каждой
  функции есть проверка `auth.uid()` и роли. До отдельного согласования не
  меняем authorization/RLS-архитектуру автоматически.

## Результат проверки окружения

- Оба проекта доступны и имеют статус `ACTIVE_HEALTHY`; live metadata подтверждает
  включённый RLS на таблицах кабинета. В миграциях дополнительно объявлен
  `FORCE ROW LEVEL SECURITY`; фактическую рольовую проверку всё равно подтверждает
  только smoke-тест.
- В production Advisor также сообщает, что защита от утёкших паролей Auth
  выключена. Это настройка Supabase Dashboard, а не изменение репозитория.
- Все четыре SQL smoke-теста завершились с `passed: true` и
  `persistent_rows: 0`. Дополнительная проверка после транзакций подтвердила
  отсутствие синтетических строк во всех связанных таблицах и объектов Storage.
- Read-only команда с отдельными браузерными access token остаётся следующим
  независимым уровнем проверки интерфейсных сессий.

## Следующий шаг

Создать отдельные обезличенные браузерные аккаунты, заполнить временные переменные из
`docs/supabase-e2e.md` и запустить `npm run supabase:smoke`. Если предупреждение о RPC
нужно устранить, сначала отдельно согласовать миграцию, которая вынесет реализации в
закрытую схему и сохранит безопасный серверный контракт.
