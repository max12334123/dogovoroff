# Supabase integration and RLS smoke tests

## Рекомендуемый способ: изолированный Supabase-стенд

Для полной проверки чтения и записи используйте только изолированную среду. Если
Supabase Branching входит в тариф, предпочтительна временная data-less Branch. Если
Branching недоступен, создайте отдельный проект Supabase на бесплатном тарифе.
Не запускайте SQL-сценарии в Production, даже несмотря на завершающий `rollback`.

1. Создайте временную Supabase Branch или отдельный бесплатный проект.
2. Примените к стенду все миграции из `supabase/migrations` в порядке версий.
3. Откройте SQL Editor именно изолированного стенда.
4. Выполните `supabase/tests/rls-isolation-smoke.sql` целиком.
5. Выполните `supabase/tests/staff-assignment-smoke.sql` целиком.
6. Выполните `supabase/tests/matter-management-smoke.sql` целиком.
7. Выполните `supabase/tests/intake-inbox-smoke.sql` целиком.
8. Выполните `supabase/tests/document-requests-smoke.sql` целиком.
9. Для всех результатов проверьте `"passed": true` и `"persistent_rows": 0`.
10. После проверки дополнительно убедитесь, что синтетические пользователи,
   организации, дела и участники не сохранились.

Первый сценарий создаёт пять обезличенных акторов и три дела внутри одной транзакции,
проверяет границы клиента A, клиента B, назначенного юриста, администратора и
анонимного посетителя. Дополнительно проверяются разрешённые и запрещённые записи
сообщений и метаданных документов. В конце выполняется `rollback`, поэтому тестовые
строки не сохраняются.

Второй сценарий проверяет административное назначение дела: клиент и юрист не могут
вызывать привилегированные RPC, администратор не может управлять чужой организацией,
неподтверждённый email отклоняется, а успешное назначение атомарно создаёт дело,
участников и первый этап. Он также завершается `rollback`.

Третий сценарий проверяет изменение статуса, этапа, следующего действия, ответственного
и реквизитов дела через узкие RPC. Четвёртый проверяет серверную запись входящей заявки,
идемпотентность, разграничение ролей, смену статуса и атомарное принятие заявки в дело.
Пятый сценарий проверяет RLS и полный цикл управляемого запроса документов: создание
сотрудником, регистрацию клиентских файлов, отправку, возврат, повторную отправку,
принятие, отмену, терминальные состояния и отсутствие чувствительного текста в событиях.

Ожидаемые контрольные показатели:

- RLS: `actors = 5`, `read_checks = 17`, `write_checks = 10`,
  `persistent_rows = 0`;
- назначение дел: `authorization_checks = 12`, `persistence_checks = 3`,
  `visibility_checks = 3`, `persistent_rows = 0`;
- управление делом: `authorization_checks = 6`, `persistence_checks = 4`,
  `persistent_rows = 0`;
- входящие заявки: `authorization_checks = 13`, `idempotency_checks = 3`,
  `conversion_checks = 6`, `persistent_rows = 0`.
- запросы документов: `authorization_checks = 12`, `transition_checks = 8`,
  `isolation_checks = 7`, `persistent_rows = 0`.

## Последний проверенный прогон

30.08.2026 первые четыре сценария успешно выполнены на отдельном бесплатном проекте
`dogovoroff-test`. Дополнительный запрос после тестов подтвердил нулевое количество
синтетических пользователей, профилей, организаций, участников, дел, этапов, событий,
документов, сообщений, записей аудита, входящих заявок и объектов Storage.
Сценарий запросов документов ещё не запускался на изолированном стенде и не разрешает
изменения Production до отдельного успешного прогона и явного подтверждения.

## Альтернативный способ: временные access token

`npm run supabase:smoke` проверяет изоляцию кабинета в подключённом проекте Supabase.
Скрипт использует только publishable key и временные access token тестовых аккаунтов.
Он не создаёт, не изменяет и не удаляет строки или объекты Storage.

## Что проверяется

- клиент A видит только дело A;
- клиент B видит только дело B;
- юрист видит только дела из своего тестового scope;
- администратор видит дела из своего тестового scope и имеет роль `admin`;
- клиентские аккаунты не читают `organization_members`;
- метаданные этапов, событий, запросов документов, документов и сообщений повторяют
  границы дел;
- клиент A не получает список объектов Storage из папки дела B;
- анонимный клиент не читает дела;
- только администратор целевой организации получает список назначаемых сотрудников;
- только администратор целевой организации создаёт назначение;
- неподтверждённый клиент и сотрудник другой организации не могут быть назначены;
- созданное дело видно назначенным клиенту и юристу.

## Подготовка тестовых данных

В Supabase Dashboard создайте четыре отдельные тестовые учётные записи и два
обезличенных дела A/B. Назначьте клиенту A только дело A, клиенту B только дело B,
юристу — согласованный набор дел, администратору — все дела тестовой организации.
Не используйте реальные клиентские документы и сообщения.

1. `before-token-smoke:` до получения токенов пройдите браузерный сценарий и
   создайте хотя бы одну строку `document_requests` для каждого ожидаемого дела из
   объединения `SUPABASE_E2E_MATTER_A_ID`, `SUPABASE_E2E_MATTER_B_ID`,
   `SUPABASE_E2E_LAWYER_MATTER_IDS` и `SUPABASE_E2E_ADMIN_MATTER_IDS`. Эти записи делают
   строгую проверку `document_requests` непустой; не удаляйте фикстуры пока.
2. `run-token-smoke:` запустите read-only smoke пока все браузерные и
   синтетические фикстуры существуют.
3. `cleanup-after-token-smoke:` только после завершения smoke удалите все
   синтетические запросы, документы, объекты Storage и остальные временные
   данные, затем подтвердите нулевые read-only counts по их UUID.

Получите access token каждой тестовой сессии обычным способом входа. Токены являются
секретами: не добавляйте их в `.env.example`, Git, issue или сообщения.

## Запуск в PowerShell

```powershell
$env:SUPABASE_E2E_ENABLED = "true"
$env:SUPABASE_E2E_CLIENT_A_TOKEN = "<temporary-client-a-access-token>"
$env:SUPABASE_E2E_CLIENT_B_TOKEN = "<temporary-client-b-access-token>"
$env:SUPABASE_E2E_LAWYER_TOKEN = "<temporary-lawyer-access-token>"
$env:SUPABASE_E2E_ADMIN_TOKEN = "<temporary-admin-access-token>"
$env:SUPABASE_E2E_MATTER_A_ID = "<matter-a-uuid>"
$env:SUPABASE_E2E_MATTER_B_ID = "<matter-b-uuid>"
$env:SUPABASE_E2E_LAWYER_MATTER_IDS = "<matter-a-uuid>"
$env:SUPABASE_E2E_ADMIN_MATTER_IDS = "<matter-a-uuid>,<matter-b-uuid>"

npm run supabase:smoke
```

Без `SUPABASE_E2E_ENABLED=true` команда завершается безопасным `skipped` и не делает
сетевых запросов. При включённом режиме неполная конфигурация завершается ошибкой до
создания Supabase-клиента. В вывод попадают только названия проверок и коды ошибок,
не токены, тексты сообщений или содержимое документов.

После проверки и cleanup фикстур удалите переменные из текущего процесса:

```powershell
Get-ChildItem Env:SUPABASE_E2E_* | Remove-Item
```
